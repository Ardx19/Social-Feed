Distributed Social Feed Engine — Complete Project Plan
Problem Statement

Build a distributed system that solves the fan-out problem: when a user posts something, how do you efficiently deliver it to all their followers — across a distributed, sharded backend — without destroying your infrastructure.

Key Schema (BadgerDB)

This is the most critical design decision. Keys are stored lexicographically — key design determines what range scans are possible.

users:{user_id}                            → User (msgpack encoded, zstd compressed)
posts:{post_id}                            → Post
posts_by_author:{author_id}:{timestamp_padded}:{post_id}   → FeedEntry (author index)
feed:{user_id}:{timestamp_padded}:{post_id} → FeedEntry
graph:followers:{user_id}:{follower_id}    → Edge
graph:following:{user_id}:{followee_id}    → Edge

Why timestamp is zero-padded: lexicographic sort must match chronological sort. 0000000001718123456 sorts correctly. 1718123456 does not at variable lengths.

Why the :{post_id} suffix on feed and author-index keys: two posts landing in the same timestamp slot would overwrite each other without it — silent post loss under tight seed loops. The suffix costs nothing and removes the failure class.

Why the author index (posts_by_author): the celebrity read path needs "recent posts by author" as a single-shard range scan. posts:{post_id} keys hash across shards by post ID, so a scan cannot find one author's posts. See read-path step 4 below and the requirements doc (R3/R4).

Why two edge directions: looking up "who follows user X" and "who does user X follow" are both O(scan) if you store both directions. Storing only one direction makes one of them O(full scan).

Consistent Hash Ring

Implement this yourself in /internal/hash. Do not use a library.

go
type Ring struct {
    nodes       []uint32          // sorted virtual node hashes
    nodeMap     map[uint32]string // virtual node hash → real node ID
    virtualNodes int
}

func (r *Ring) AddNode(nodeID string)
func (r *Ring) RemoveNode(nodeID string)
func (r *Ring) GetNode(key string) string

Virtual nodes: each physical node gets N virtual positions on the ring (e.g. N=150). Without virtual nodes, distribution is uneven. With them, each physical node owns roughly equal keyspace.

GetNode logic: hash the key, find the first virtual node clockwise on the ring (binary search on sorted array), return its physical node.

Fan-out Logic

This is the core of the project. Lives in /internal/fanout.

Write path (user creates a post)
1. Store post on author's shard
2. Check author's FollowerCount
3. If FollowerCount < threshold (1000):
     → Fan-out on write
     → Fetch all follower IDs from graph:followers:{author_id}:*
     → For each follower, write FeedEntry to feed:{follower_id}:{timestamp}
     → Do this in parallel using goroutines
     → If a shard is down, log failure, continue (partial fan-out)
4. If FollowerCount >= threshold:
     → Do nothing. Post is stored. No fan-out.
Read path (user opens feed)
1. Fetch precomputed feed entries from feed:{user_id}:* (range scan, latest N)
2. Fetch list of followees from graph:following:{user_id}:*
3. Filter followees where FollowerCount >= threshold (celebrities)
4. For each celebrity, fetch their recent posts from posts_by_author:{celeb_id}:* (author index, single-shard range scan)
5. Merge all entries by timestamp descending
6. Return top N
The merge problem

Step 5 is a scatter-gather — you're fetching from potentially multiple shards simultaneously. Use goroutines, collect results into a channel, merge after all return.

Replication

Each shard has one replica. Kept simple intentionally.

Write flow:

Coordinator writes to primary shard
Primary shard asynchronously replicates to its replica
Coordinator does not wait for replica acknowledgment (async = eventual consistency)

Failure detection:

Coordinator pings each node every 5 seconds (heartbeat)
If 3 consecutive pings fail, node marked as down
If primary is down, coordinator routes reads to replica
Writes to a down primary are queued in memory (small buffer), retried when primary recovers

What this does not handle:

Split brain (primary and replica both think they're primary)
Data loss if primary dies before replicating
These are Raft's job — acknowledge this explicitly

Frontend (React + Vite)

Three views, nothing more:

Feed View — default landing page

Input: enter user ID
Shows merged feed (posts from followees, celebrities included)
Infinite scroll or simple pagination

Post View

Input: user ID + post content
Submit → POST /posts
Show success confirmation

Follow View

Input: follower ID + followee ID
Follow / unfollow buttons
Show current following list for a user

No auth, no sessions, no state management library. Plain React useState + fetch.

Known Gaps (document these, don't hide them)
Gap	Production solution	Why skipped
No consensus protocol	Raft for leader election	Too complex for scope
Async replication = data loss possible	Synchronous replication + Raft	Tradeoff accepted for simplicity
No Kafka	Fan-out via event queue	Adds infra, coordinator handles it directly
No Redis feed cache	Redis as read-through cache	Time
HTTP not gRPC	gRPC for shard communication	Learning overhead
Celebrity threshold is static	Dynamic threshold based on load	Time
No auth	JWT + middleware	Out of scope
Single coordinator = SPOF	Multiple coordinators + load balancer	Acknowledged
